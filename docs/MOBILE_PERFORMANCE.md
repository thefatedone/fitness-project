# Производительность на физических телефонах

Статус: подписанная Profile-сборка установлена и запущена на физическом iPhone
(iPhone18,3, iOS 27.0); подключение Dart VM Service подтверждено. Первая выборка
после запуска: 600 кадров, дисплей 120 Гц, build p95 0.768 мс, raster p95 2.575 мс,
0 кадров с этапом выше бюджета. Сценарий этой выборки не размечен: это диагностика
запуска, а не воспроизводимый тест прокрутки, измерение FPS или сравнение до/после.
Замеры памяти и отдельные сценарии ещё не выполнены.

## Запуск

1. Подключить физический телефон; `flutter devices` должен показать mobile,
   не simulator. На iPhone включить Developer Mode, подтвердить доверие к Mac.
2. Для первого запуска iOS открыть `flutter_app/ios/Runner.xcworkspace` в Xcode.
   В Settings → Accounts добавить свой Apple Account. В Runner → Signing &
   Capabilities выбрать свою Team и Automatic Signing. Не публиковать приложение.
   Если идентификатор занят, выбрать уникальный Bundle Identifier в Xcode.
3. Запустить локальный сервер через `make dev` из корня проекта. Телефон и Mac
   должны быть в одной локальной сети. Разрешить доступ к локальной сети на iPhone.
4. Из корня проекта:

   ```sh
   ./scripts/profile_mobile.sh DEVICE_ID
   ```

   На Mac скрипт определяет LAN-адрес основного интерфейса. Если используется
   VPN, нестандартный порт или удалённый сервер, указать адрес явно:

   ```sh
   API_BASE_URL=http://192.168.1.20:8000 ./scripts/profile_mobile.sh DEVICE_ID
   ```

   `localhost` на физическом телефоне указывает на сам телефон.
   Явный `API_BASE_URL` имеет приоритет над сохранённой настройкой debug-сервера.
   Это адрес сервера без секретов; не передавать учётные данные в URL.

В VS Code добавлена конфигурация **NutriMind iPhone / Android (profile + metrics)**.
Она спрашивает URL сервера. Debug-конфигурация с hot reload остаётся для разработки.
В Profile hot reload недоступен. Не сравнивать скорость Debug и Profile как
результат оптимизации: для до/после нужен один и тот же режим, телефон и сценарий.

## Воспроизводимые сценарии

После входа в свою учётную запись, без изменения или удаления существующих данных:

- 30 секунд прокручивать дневник вверх/вниз, раскрывать сохранённые блюда.
- Открыть сад, дождаться загрузки изображений; прокручивать и менять предпросмотр
  стадий ещё 30 секунд. Отдельно отметить задержку первого открытия.
- Выбрать крупную фотографию камеры. Проверить её отображение. Реальное AI-
  распознавание проверять отдельно: оно отправляет фото и создаёт запись дневника.
- Свернуть/открыть приложение несколько раз, проверить навигацию и прокрутку.

Для сравнения до/после использовать одинаковое количество записей, один файл фото,
одинаковые настройки темы/доступности и сеть. Записать модель, версию iOS/Android,
заряд/режим энергосбережжения и нагрев телефона. Повторить сценарий 3 раза.

## Метрики

Только при `--profile --dart-define=PERF_METRICS=true` приложение выводит строки
`NUTRIMIND_PERF` в консоль. Каждая содержит максимум последние 600 кадров с
UI/raster p50/p95/max, частотой дисплея и числом кадров, у которых один из этапов
превысил бюджет. Окна печатаются по мере поступления кадров, не чаще раза в 10 сек.
При уходе в фон окно сбрасывается. Нет отправки данных наружу, фото, URL, токенов
или записей дневника в отчёте. Обычные debug/release-запуски монитор не включают.

Бюджет при 60 Гц — около 16.67 мс, при 120 Гц — 8.33 мс. UI и raster работают
конвейером, поэтому их времена не складываются. Частота дисплея может отличаться
от фактической адаптивной частоты рендеринга. `over_budget_frames` — диагностический
счётчик, а не точное количество пропущенных экраном кадров и не измеренный FPS.

DevTools → Performance: записать каждый сценарий отдельно, исследовать длинные
UI/raster-кадры. DevTools → Memory: сравнить память после открытия фото, после
закрытия и после повторения 10 раз. Для памяти native/GPU и запуска приложения
использовать Xcode Instruments; длительность AI/сети учитывать отдельно от кадров.

## Внесённые изменения

- Фото предпросмотра декодируются с сохранением пропорций в пределах 2048×2048,
  без увеличения маленьких исходников. Оригинал для AI остаётся неизменным.
  Один такой RGBA-буфер занимает максимум около 16 МиБ; это не оценка памяти
  всего приложения. Тест проверяет настоящий декодер на большом PNG.
- Фото во время переходной анимации передаётся как статический child, вместо
  перестроения его поддерева на каждом кадре.
- Группировка ингредиентов дневника выполняется за один проход, сохраняя порядок
  блюд и отдельные ручные записи. Устранены вложенные поиски по всем ингредиентам.
- Добавлены профиль запуска и явный адрес API для физического устройства.
- Android разрешает локальный HTTP в profile-варианте. iOS объявляет локальный
  сетевой доступ и локальное исключение ATS, без глобального отключения ATS.

Правила локальной сети iOS: [Apple — NSAllowsLocalNetworking](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking).
